## 1. Veredito sobre os achados do agente pai (A–E)

| Achado | Veredito | Argumento (com evidência) |
| :--- | :--- | :--- |
| **A** — 3 structs de evento, 1 corpo de POST, transporte indefinido | **CONFIRMADO (blocker)** | `webhooks.go:57-107` define 3 structs, mas todos os artefatos existentes assumem **um único corpo**: `docs/04` §4 (L72-90) documenta o payload como um único JSON; `docs/02-ARCHITECTURE.md:110` (`NORM->>WH: WebhookInboundEvent`); `apps/api/README.md:15` diz que o normalizador mapeia `*events.Message`/`*events.GroupInfo` → `contracts.WebhookInboundEvent`; `openapi.yaml:1213` declara o `data:` do SSE como `WebhookInboundEvent` apenas. Não há como um agente distinguir se o POST é Inbound/Group/Session. Recomendação: **envelope único** — `WebhookInboundEvent` vira o único corpo, com `group` e `session` como campos opcionais (`omitempty`) e `event_type` como discriminador dos 5 valores. Rejeito corpo polimórfico (complica unmarshal Go/Huma e obriga cada agente a branchear por forma) e raw JSON (perde tipagem/doc, contradiz o papel de "normalizador"). |
| **B** — `PollVote.Question`/`SelectedOptions` obrigatórios não representam cache-miss | **CONFIRMADO (major)** | `webhooks.go:39-40` sem `omitempty`: sem a criação da enquete no SQLite (enquete antiga, cache perdido) o normalizador emitiria `"question": ""` e `"selected_options": null` — indistinguíveis de um voto real sem seleção. Nota técnica: `DecryptPollVote` (`msgsecret.go:305`) devolve `*waE2E.PollVoteMessage` com `SelectedOptions [][]byte` = hashes SHA-256 dos **nomes** (`msgsecret.go:369` `HashPollOptions`), e um voto de "remoção de seleção" chega com lista vazia — então os 3 estados (voto com seleção, remoção de voto, cache-miss) precisam ser distinguíveis. Correção: `omitempty` em `question` e `selected_options` + doc explícita; `selected_hashes` permanece sempre presente (derivável do upstream). |
| **C** — `DownloadURL`/`ExpiresAt` obrigatórios vs `AutoDownloadMedia` | **CONFIRMADO (major)** | Com `auto_download_media=false` não há arquivo servível em `GET /api/v1/media/{id}` (decisão 4 do dono), mas `webhooks.go:51-52` força `"download_url": ""` e `"expires_at": "0001-01-01T00:00:00Z"` (zero-value de `time.Time`) no JSON. Correção: `omitempty` em ambos (ou `*time.Time`) + doc "presentes somente quando o gateway armazenou o arquivo". Complemento meu: falta `media_id` (o mesmo id de `MediaRef`, `common.go:34-41`) para o agente re-solicitar antes do TTL após um 410. |
| **D** — `MessageType` string livre | **CONFIRMADO (major), com agravo** | Além de não tipado, os dois vocabulários **divergem**: `webhooks.go:71` lista `text, image, audio, video, document, button_reply, list_reply, poll_vote, reaction`; `messages.go:156` (`MessageSummary.message_type`) lista `text, image, audio, video, document, sticker, poll, reaction, button_reply, list_reply`. Mesmo conceito, duas listas, ambas incompletas. Correção: tipo `WebhookMessageType` + constantes + `enum` tag, e reuso idêntico em ambos os structs. |
| **E** — `EventType` duplicado nos eventos de grupo/sessão | **CONFIRMADO (minor, contingente a A)** | Sob envelope único (minha recomendação para A), `WebhookGroupEvent.EventType` (`webhooks.go:90`) e `WebhookSessionEvent.EventType` (`webhooks.go:102`) duplicam o discriminador do envelope com enum de valor único — fonte dupla de verdade que diverge com o tempo. Correção: remover os campos e renomear os structs para papéis de payload (`WebhookGroupSnapshot`, `WebhookSessionSnapshot`). `EventType` interno só faria sentido se a opção fosse corpo polimórfico, que descarto. |

## 4. O que está correto (não mexer)
- Doc tags **pt-BR em 100% dos campos exportados** dos 4 arquivos verificados; JSON 100% snake_case; `WebhookEventType` e `WebhookGroupChangeType` têm constantes + `enum` tag nos pontos de uso.
- `IsFromMe` (L69) existe e casa nominalmente com `IgnoreFromMe` (L113) — a incoerência é só semântica/doc (W-10), não de campo.
- `WebhookPollVote.SelectedHashes` (L41) é o campo certo para o fallback: é derivável sempre (`msgsecret.go:305/369`), independe de cache.
- Separação struct de request (Huma valida entrada) vs structs de webhook (somente saída) está coerente; `Problem` (RFC 9457) em `common.go` está correto para a regra "limites do WhatsApp → 4xx" (decisão 9).

**REPROVADO nesta versão.** Dois blockers (W-01: transporte de eventos indefinido para group/session; W-02: reação declarada sem payload) e onze majors que incluem os casos de cache-miss de enquete, mídia sem download e segredo ecoado na resposta — todos confirmados contra o upstream `ecc39170bc14`. A base é boa (tipagem de enums, doc pt-BR completo, hashes de voto); as correções são majoritariamente aditivas e de baixo custo (omitempty, campos extras, envelope único), viáveis em um único passe sobre `webhooks.go` + regeneração do `openapi.yaml` antes de codificar o normalizador em S2.
